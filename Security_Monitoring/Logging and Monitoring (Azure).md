# Azure Logging, Monitoring, and Security Detection

## Purpose

This module demonstrates an Azure logging and monitoring pattern using Azure Monitor, Log Analytics, diagnostic settings, and alerting.

For this scenario, the objective is to collect security-relevant telemetry from Azure resources and use that telemetry to support detection, investigation, and response.

The architecture pattern is:

**Azure Resource → Diagnostic Settings → Log Analytics → Detection Logic → Alert → Investigation / Response**

Enabling logging alone does not establish a working security detection capability.

---

## 1. Create a Log Analytics Workspace

Example:

```bash
az monitor log-analytics workspace create \
    --resource-group monitoring-rg \
    --workspace-name security-workspace \
    --location eastus
```

The workspace provides a centralized location for selected Azure telemetry.

### Production Considerations

For a production environment, I would also evaluate:

* Workspace architecture
* Regional requirements
* Data residency
* Access control
* Retention
* Cost
* Table configuration
* Monitoring ownership
* Integration with Microsoft Sentinel or another enterprise SIEM where required

The organization should determine which telemetry belongs in the workspace rather than automatically collecting everything.

---

## 2. Configure Diagnostic Settings

Azure resources can use diagnostic settings to send supported logs and metrics to destinations such as Log Analytics.

Conceptually:

```text
Azure Resource
      │
      ▼
Diagnostic Settings
      │
      ▼
Log Analytics
```

The specific categories available depend on the resource type.

For this scenario, the target resource is an Azure Storage account.

Before configuring diagnostic settings, I would verify the currently supported log categories for that resource rather than assuming the same categories apply to every Azure service.

---

## 3. Determine Required Telemetry

The security requirement should determine what telemetry is collected.

For sensitive-data monitoring, useful questions include:

* Which storage operations need visibility?
* Which identities performed them?
* Which resources were accessed?
* Were the operations successful?
* Where did the requests originate?
* Was the activity expected?
* Does the data classification justify additional monitoring?

This is more useful than simply collecting logs because they are available.

---

## 4. Detection Logic

The original project example used:

```text
Total Requests > 100
```

as the trigger for a sensitive-data-access alert.

That threshold could indicate unusual volume, but it does **not by itself establish that sensitive data was accessed**.

I would separate the two use cases.

### Volume Anomaly

**Request Volume → Threshold / Baseline → Alert**

This can detect unexpectedly high storage activity.

### Sensitive Data Access

**Relevant Access Telemetry → Identity + Resource + Operation + Context → Detection → Alert**

This requires telemetry that actually provides the context necessary to identify the access being monitored.

---

## 5. Query-Based Detection

Where appropriate telemetry exists in Log Analytics, KQL can be used to identify activity relevant to the security use case.

Conceptually:

```text
Telemetry
    │
    ▼
KQL Detection Logic
    │
    ▼
Matching Events
    │
    ▼
Azure Monitor Alert
```

The actual query should be based on the log schema generated by the resource.

I would validate the available tables and fields before creating the production detection.

---

## 6. Alert Design

An alert should represent a condition that warrants investigation.

Potential detection scenarios could include:

* Unexpected administrative changes
* Logging being disabled
* Unusual access volume
* Access from an unexpected identity
* Access from an unexpected network location
* Repeated authorization failures
* High-risk configuration changes
* Security-control modification

Thresholds should be based on expected workload behavior and risk rather than arbitrary values.

---

## 7. Alert Response

The response path should be defined before the alert is considered operational.

Conceptually:

**Detection → Alert → Investigation → Risk Decision → Response**

An analyst may need to determine:

* Which identity generated the activity?
* Which resource was affected?
* Was the activity expected?
* What data was potentially involved?
* Were permissions appropriate?
* Did other suspicious activity occur?
* Is containment required?

Not every alert should automatically trigger a disruptive response.

---

## 8. Telemetry Health

The monitoring system itself needs monitoring.

If diagnostic settings are removed or telemetry stops reaching Log Analytics, the detection capability may silently fail.

I would therefore consider monitoring for:

* Diagnostic-setting changes
* Missing expected telemetry
* Workspace configuration changes
* Access-control changes
* Alert-rule changes
* Collection failures

A detection architecture should be able to identify when its own visibility has been degraded.

---

## 9. Identity and Access

Access to monitoring data should follow least privilege.

I would define:

* Who can query logs
* Who can change diagnostic settings
* Who can create or modify alerts
* Who can administer the workspace
* Which automation identities can access telemetry

Monitoring data may itself contain sensitive operational or security information.

---

## 10. Retention and Cost

Log retention should reflect:

* Security investigation requirements
* Compliance obligations
* Business criticality
* Incident-response needs
* Query frequency
* Cost

More logging is not automatically better if the organization cannot operate, analyze, or retain it effectively.

---

## 11. Failure Paths

### Diagnostic Settings Removed

If diagnostic settings are deleted or changed, required telemetry may stop flowing.

The organization should detect and investigate the configuration change.

### Log Analytics Ingestion Failure

If telemetry fails to reach the workspace, dependent detections may stop functioning.

The architecture should include a way to detect missing telemetry.

### Alert Delivery Failure

An alert that cannot reach the responsible team provides little operational value.

Notification and escalation paths should therefore be tested.

---

## 12. Evidence

Useful evidence from this architecture could include:

* Log Analytics workspace configuration
* Diagnostic settings
* Enabled telemetry categories
* Retention configuration
* Detection queries
* Alert rules
* Alert history
* Access-control configuration
* Investigation records

This demonstrates the path from telemetry collection to operational security use.

---

## ISO 27001 Context

This architecture can support organizational security requirements involving:

* Event logging
* Monitoring
* Detection
* Administrative accountability
* Incident response
* Evidence preservation

The exact relationship to ISO/IEC 27001 depends on the organization's ISMS scope, risk assessment, Statement of Applicability, architecture, and control design.

Azure Monitor or Log Analytics should not be treated as proof of ISO 27001 compliance by themselves.

---

## Architecture Takeaway

For this scenario, I would use:

**Required Security Event → Azure Telemetry → Diagnostic Settings → Log Analytics → Detection Logic → Alert → Investigation → Response → Evidence**

The important question is not:

**“Did we enable Azure logging?”**

It is:

**“Are we collecting the right event, can we detect the behavior that matters, and does someone know what to do when the alert fires?”**
